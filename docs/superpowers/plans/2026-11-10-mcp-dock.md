# MCP Dock Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A Go binary that serves one streamable HTTP MCP endpoint, protected by its own OAuth 2.1 server that delegates login to GitHub, and proxies tools from several supervised stdio MCP upstreams (jaypost first).

**Architecture:** One `mcp.Server` instance holds the merged, prefixed tool list; each tool handler routes to an upstream supervisor that owns one shared `mcp.ClientSession` over `mcp.CommandTransport`. An `oauth` package implements metadata, DCR, authorize (redirect to GitHub), consent, and token endpoints over a SQLite store; its `Verify` method plugs into the SDK's `auth.RequireBearerToken` middleware in front of `/mcp`.

**Tech Stack:** Go 1.27, `github.com/modelcontextprotocol/go-sdk` v1.8.0 (`mcp`, `auth`, `oauthex`), `modernc.org/sqlite` (pure Go, no cgo, container friendly), `go.yaml.in/yaml/v3`, `log/slog`, stdlib `net/http`.

**Spec:** `docs/superpowers/specs/2026-11-10-mcp-dock-design.md`

## Global Constraints

- Module path: `github.com/bithyte/mcp-dock`. Binary: `mcp-dock`.
- Tool names exposed as `<server_name>__<tool_name>` (two underscores), e.g. `jaypost__ask_user`.
- Upstream `name`: lowercase letters, digits, single `_` or `-`; no `__`. Regex: `^[a-z0-9]+([_-][a-z0-9]+)*$`. Bad config fails startup.
- Exposed tool names must match `^[a-zA-Z0-9_-]{1,64}$`; upstream tools that don't fit after prefixing are skipped with a warning log.
- Secrets only from env vars, never the config file. Never log tokens, secrets, tool arguments, or tool results.
- Upstream process env: only `PATH`, `HOME`, the upstream's `env`, and its `env_from` vars. Not the gateway's environment.
- Upstream working dir: an empty dir `<data_dir>/upstreams/<name>/cwd`.
- OAuth: PKCE S256 only. Access token TTL 1h. Refresh token TTL 30 days, rotated on every use, reuse rejected. Tokens and codes stored as SHA-256 hashes.
- Allowlist: GitHub login, case-insensitive, checked at login, at token issue/refresh, and on every MCP request.
- Known login mapping to a different GitHub numeric ID: deny and log a warning. Recovery: `mcp-dock users reset <login>`.
- Consent page after GitHub login, remembered per (login, client_id).
- Must accept Claude's redirect `https://claude.ai/api/mcp/auth_callback` and loopback redirects (`http://localhost`, `http://127.0.0.1`, `http://[::1]`, any port).
- `public_url` comes from config, never from request headers. MCP endpoint is `<public_url>/mcp`; that string is the OAuth resource.
- Logs: JSON `slog` to stdout. Per tool call: `user`, `tool`, `duration_ms`, `ok`.
- `/healthz` is unauthenticated and returns only `ok`.
- Tools only; no resources or prompts forwarded.
- Commits: one per task as written. Never stage anything under `docs/superpowers/` (the owner asked not to commit those).

## Review Focus

1. Upstream command missing or failing at startup (jaypost not on `PATH`): gateway still starts, serves other upstreams, logs, and retries with backoff. Test in Task 4.
2. One user's long blocking call (jaypost `ask_user` waits minutes) must not delay another user's call on the same upstream. Test in Task 5.
3. `public_url` with a trailing slash, or a client sending `resource` with/without a trailing slash: both normalize to the same resource; tokens still verify. Test in Tasks 1 and 9.
4. `deny_args` against odd arguments: missing `arguments`, `null`, `attachment` as a string, schema without `properties`. No panic; reject only when the denied path is actually present. Test in Task 3.
5. Upstream tool names that become invalid or longer than 64 chars after prefixing: skipped with a warning, rest of that upstream's tools still exposed. Test in Task 5.

### Task 8: Authorize, GitHub callback, consent

**Files:**
- Create: `internal/oauth/authorize.go`, `internal/oauth/templates.go`
- Test: `internal/oauth/authorize_test.go`

**Interfaces:**
- Consumes: Task 7 `Server`, store `AuthRequest`/`Code`/consent/GitHub ID methods, `github.Client`.
- Produces: the HTTP behavior below; `func (s *Server) issueCode(w http.ResponseWriter, r *http.Request, ar *store.AuthRequest)` used by both callback (consent remembered) and consent POST.

Behavior:
- `GET /authorize`: unknown `client_id` or redirect_uri not registered → HTML error page 400, no redirect. Redirect match is exact, except loopback hosts where port is ignored. After that, errors redirect to `redirect_uri?error=...&state=...`: `response_type != code` → `unsupported_response_type`; missing `code_challenge` or method not `S256` → `invalid_request`; `resource` present and `NormalizeURL(resource) != ResourceURL()` → `invalid_target`. Success: save AuthRequest (TTL 10 min, ID = `newSecret()`), set cookie `mcpdock_auth=<ID>` (HttpOnly, SameSite=Lax, Path `/oauth/`, Secure when PublicURL is https), 302 to `GitHub.AuthorizeURL(ID, PublicURL+"/oauth/github/callback")`.
- `GET /oauth/github/callback`: `state` must match an unexpired AuthRequest AND the cookie value, else 400 page. Exchange code, fetch user. Not `IsAllowed` → 403 page "GitHub account <login> isn't allowed on this gateway." Stored ID exists and differs → 403 page + `Warn` log with login and both IDs. No stored ID → `SetGitHubID`. `SetAuthRequestUser`. If `HasConsent(login, client)` → `issueCode`. Else render consent page.
- Consent page: shows client name, redirect URI host, the GitHub login; form POST `/consent` with hidden `request` = AuthRequest ID; buttons `approve` / `deny`. Headers on every HTML response: `X-Frame-Options: DENY`, `Content-Security-Policy: frame-ancestors 'none'`, `Cache-Control: no-store`.
- `POST /consent`: AuthRequest must exist, have a Login set, and match the cookie. `deny` → redirect `error=access_denied`. `approve` → `SaveConsent`, `issueCode`.
- `issueCode`: code = `newSecret()`, store hash, TTL 5 min; delete AuthRequest; clear cookie; 302 to `redirect_uri?code=..&state=<ClientState>&iss=<PublicURL>`.

### Task 9: Token endpoint and verifier

**Files:**
- Create: `internal/oauth/token.go`
- Test: `internal/oauth/token_test.go`

**Interfaces:**
- Consumes: Task 8 codes; store token methods.
- Produces:
  ```go
  func (s *Server) Verify(ctx context.Context, token string, r *http.Request) (*auth.TokenInfo, error)
  // matches auth.TokenVerifier; returns auth.ErrInvalidToken (wrapped) on any failure;
  // success: TokenInfo{UserID: login, Expiration: t.ExpiresAt, Scopes: nil}
  ```

Behavior of `POST /token` (form-encoded):
- Client auth by registered method: `none` needs only `client_id`; `client_secret_post` reads `client_secret` form field; `client_secret_basic` reads Basic header. Failure → 401 `invalid_client`.
- `authorization_code`: `ConsumeCode(hash(code))`; code's ClientID == client; `redirect_uri` equals the one used at authorize; PKCE `base64url(sha256(code_verifier)) == CodeChallenge`; `resource`, if sent, normalizes to `ResourceURL()`; login still `IsAllowed`. Any failure → 400 `invalid_grant` (or `invalid_target` for resource).
- `refresh_token`: `ConsumeRefreshToken`; same client; login still allowed; issue a new pair (rotation). Reused or unknown → 400 `invalid_grant`.
- Success JSON: `access_token`, `token_type: "Bearer"`, `expires_in: 3600`, `refresh_token`, `scope` if any. Headers `Cache-Control: no-store`.
- Unknown grant → 400 `unsupported_grant_type`.
- `Verify`: `GetToken(hash)`, `Kind == "access"`, not expired, `Resource == ResourceURL()`, `Config.IsAllowed(login)`.
